처음에는 준비된 예시 답변을 읽고 발표하려고 했다. 그런데 내가 직접 생각해서 쓴 내용이 아니다 보니, 왜 그렇게 답하는지 설명하려면 막히는 부분이 있었다. 그래서 예시를 외우는 대신 내 생각부터 이야기하고, 반박과 질문을 거치면서 네 가지 답변을 다시 정리했다.

네 질문을 따라가면서 계속 돌아오게 된 생각은 비슷했다. **무엇을 해결해야 하는지 먼저 정확하게 정의하고, 그다음에 도구를 선택해야 한다는 것**이다. 다만 그렇게 말하는 것만으로는 부족했다. 날짜의 의미를 코드로 어떻게 표현할지, 모델의 학습된 값을 어디에 보관할지, NumPy가 왜 빠를 수 있는지까지 설명할 수 있어야 했다.

*공식 문항에 대한 내 견해를 대화로 다듬고 AI의 도움을 받아 글로 정리했다. 아래 코드·메모리 주소·처리 시간은 이해를 돕기 위한 예시이며, 실제 회사 업무나 성능 측정 결과가 아니다. 여러 주제를 다룬 위클리 페이퍼로, 사이트에서는 파이썬 기초 복습 아래에 묶었다.*

## 1. AI 엔지니어에게 가장 중요한 역량은 무엇인가?

> AI 엔지니어에게 가장 중요한 역량은 무엇이라고 생각하나요? 기술적 역량과 비기술적 역량 중 하나를 선택하고, 그 이유를 본인의 언어로 설명해 주세요.

나는 **해결해야 할 문제를 정확하게 정의하는 능력**이 가장 중요하다고 생각한다. 기술적 역량과 비기술적 역량 중 하나를 고르라면 비기술적 역량에 더 가깝다고 보겠다. 사용자나 동료에게 질문하고, 서로 다르게 이해한 요구를 맞추고, 무엇을 성공으로 볼지 합의하는 데서 시작하기 때문이다.

처음에는 이 능력을 “AI에게 무엇을 해결할지 정확하게 전달하는 능력”이라고 생각했다. 나는 앞으로 AI가 코드를 작성하는 비중이 크게 늘 것이라고 예상한다. 그래서 사람이 직접 구현하는 능력만큼이나 어떤 문제를 풀어야 하는지 결정하는 능력이 중요해질 것이라고 봤다.

다만 이 질문의 AI 엔지니어는 AI로 코딩하는 사람만을 뜻하지 않는다. **서비스에 AI를 접목해서 문제를 푸는 사람**이다. 그렇다면 질문도 “AI에게 코드를 어떻게 시킬까?”에서 “이 서비스의 어떤 문제에 AI가 필요한가?”로 넓어져야 한다.

예를 들어 고객이 원하는 정보를 찾기 어려워한다면, 바로 AI 챗봇을 붙이는 것부터 결정하지는 않을 것 같다. 어떤 정보를 못 찾는지, 기존 검색이나 화면을 고치는 것으로 해결할 수는 없는지부터 확인해야 한다. AI가 적절한 방법이라면 그때 사용할 데이터와 평가 기준을 구체화해야 한다. 모델의 정답률이 높아졌더라도 응답이 너무 느리거나 비용이 너무 커서 서비스에서 쓸 수 없다면 문제를 해결했다고 보기 어렵다.

여기서 내 생각이 바뀐 부분도 있다. 처음에는 문제 정의가 정확하면 AI가 만든 결과를 검증하는 과정도 잘 설계할 수 있다고 생각했다. 하지만 요구가 정확하다는 것과, AI가 그 요구를 실제로 지켰다는 것은 별개였다. 검사 자체를 잘못 만들 가능성도 있다. 사람이 모든 결과를 하나씩 확인하면 병목이 될 수 있으니, 실패했을 때의 영향에 따라 자동으로 검사할 부분과 사람이 판단할 부분을 나누는 설계가 필요하다고 본다.

내가 중요하게 보는 책임도 이 판단과 연결된다. AI가 결과를 만들어 주더라도, 그 결과를 서비스에 적용할 기준을 정하고 문제가 생겼을 때 대응하는 책임을 AI에게 넘겼다고 말할 수는 없다. 엔지니어와 조직이 감당해야 할 일이다.

그래서 내 답은, **사용자의 문제를 이해하고 그것을 AI가 다룰 수 있는 과제와 성공 기준으로 바꾸는 능력**이다. 출발점은 비기술적인 문제 정의지만, 실제로 구현하고 검증하려면 기술적인 이해가 함께 필요하다.

## 2. 기존 모듈에 회사만의 날짜 표현 처리 기능이 없다면?

> 날짜 데이터를 정리하는 기능이 필요해서 찾아보니, 이미 있는 모듈이 내가 원하는 기능의 대부분(요일 계산, 날짜 간격 계산)을 갖고 있어요. 그런데 딱 하나, 우리 회사만 쓰는 특이한 날짜 형식(예: '25년 3월 첫째 주')을 처리하는 기능만 빠져 있어요. 어떻게 할 건가요?

나는 먼저 회사 사람들이 **“25년 3월 첫째 주”를 정확히 어떤 기간으로 사용하는지 물어볼 것**이다. 익숙한 표현이라고 해서 모두가 같은 날짜를 떠올리는 것은 아니기 때문이다.

예를 들어 2025년 3월 1일이 포함된 월요일부터 일요일이라면 2월 24일부터 3월 2일까지다. 반면 그달의 첫 일곱 날을 뜻한다면 3월 1일부터 3월 7일까지다. 이건 혼자 고민해서 정답을 찾을 문제가 아니라, 실제로 그 표현을 사용하는 사람들에게 회사의 규칙을 확인해야 하는 문제라고 생각한다.

여기서는 **3월 1일부터 3월 7일까지이며 양끝 날짜를 모두 포함한다**고 확인했다고 가정하겠다. 다음으로는 기존 모듈이 무엇을 제공하는지 살펴보고, 이미 있는 기능을 가져다 쓸 것이다. 새로 필요한 부분은 회사의 표현을 읽어서 시작 날짜와 종료 날짜로 바꾸는 함수다.

결과는 다음처럼 딕셔너리로 표현할 수 있다.

```python
from datetime import date

period = {
    "start": date(2025, 3, 1),
    "end": date(2025, 3, 7),
}
```

처음에는 3월 1일과 7일의 요일부터 구해야 한다고 생각했다. 하지만 “그달의 첫 일곱 날”이라는 규칙이라면 요일이 무엇인지는 기간을 정하는 데 필요하지 않다. 연도와 월, 주차를 읽고 회사의 규칙을 적용하면 된다.

시작 날짜에서 종료 날짜를 구할 때는 날짜에 일수를 더하는 기능을 사용할 수 있다. 다만 날짜 간격을 계산하는 기능과 날짜에 일수를 더하는 기능은 다르므로, 기존 모듈이 둘 다 제공하는지는 확인해야 한다. 파이썬 표준 라이브러리에서는 다음처럼 표현한다.

```python
from datetime import date, timedelta

start = date(2025, 3, 1)
end = start + timedelta(days=6)
period = {"start": start, "end": end}
```

두 날짜의 차이는 6일이지만, 1일과 7일을 모두 세면 포함된 날짜는 7개다. 이 구분까지 함수의 반환 규칙에 적어 두겠다. 위 코드는 규칙을 적용한 작은 예이며, 문자열을 해석하는 전체 함수는 아니다.

결국 기존 날짜 계산을 전부 다시 만들기보다는, **회사의 암묵적인 규칙을 명확히 확인하고 그 규칙을 기존 모듈과 연결하는 부분만 추가**할 것 같다.

## 3. PyTorch 모델을 굳이 클래스로 정의하는 이유는?

> PyTorch로 딥러닝 모델을 만들 때, 굳이 클래스로 모델을 정의하는 이유가 무엇일까요? 함수만으로 구현하는 방식과 비교해서 설명해 주세요.

내가 이해한 가장 큰 이유는 **모델이 사용하는 파라미터와 그 파라미터로 계산하는 기능을 하나의 객체로 묶어 관리할 수 있기 때문**이다.

PyTorch는 딥러닝 모델을 만들고 학습시키는 데 사용하는 프레임워크다. 아직 구체적인 PyTorch 사용법을 배우기 전이라, 여기서는 클래스와 객체의 관점에서 설명해 보려고 한다.

딥러닝 모델은 입력을 받아 예측값을 만들고, 학습 과정에서 예측의 오차를 줄이는 방향으로 파라미터를 갱신한다. 내가 처음 설명할 때는 파라미터를 예측값이라고 표현했는데, 둘은 다르다. 파라미터는 **예측값을 만드는 데 사용하는 가중치와 편향 같은 학습 대상 값**이다.

아주 단순하게 `예측값 = 입력 × 가중치 + 편향`이라고 생각해 보자. 입력이 3이고 가중치가 2, 편향이 1이면 예측값은 7이다. 학습으로 가중치와 편향이 바뀌면, 다음 예측에는 바뀐 값을 사용해야 한다. 따라서 계산이 한 번 끝났다고 그 값이 사라져서는 안 된다.

함수로도 구현할 수 있다.

```python
def predict(x, params):
    return x * params["weight"] + params["bias"]

params_a = {"weight": 2, "bias": 1}
params_b = {"weight": 5, "bias": 0}

predict(3, params_a)  # 7
predict(3, params_b)  # 15
```

이 방식도 파라미터를 보관할 수 있다. 다만 함수를 호출하는 쪽에서 어떤 모델의 파라미터를 넘길지 함께 관리한다. 클래스로 묶으면 그 관계를 모델 객체 내부에 표현할 수 있다.

```python
class Model:
    def __init__(self, weight, bias):
        self.weight = weight
        self.bias = bias

    def predict(self, x):
        return x * self.weight + self.bias

model_a = Model(2, 1)
model_b = Model(5, 0)

model_a.predict(3)  # 7
model_b.predict(3)  # 15
```

*위 코드는 상태와 계산을 묶는 모습을 보여 주는 일반 파이썬 예제이며, PyTorch 학습 코드가 아니다.*

호출하는 입장에서는 `model_a`에 입력을 주면 그 객체가 가진 파라미터로 계산한다는 것을 바로 알 수 있다. 같은 구조의 모델을 여러 개 만들어도 각각 다른 값을 보관하고, 별도로 학습시킬 수 있다. 이 예시에서도 `model_a.weight`를 바꿔도 `model_b.weight`는 바뀌지 않는다.

나는 이 점에서 클래스가 직관적이라고 느꼈다. “함수는 값을 저장할 수 없다”거나 “함수 방식에는 객체가 없다”는 뜻은 아니다. 파이썬에서는 함수와 딕셔너리도 객체다. 차이는 **모델의 상태와 동작을 하나의 단위로 묶어서 표현하느냐**에 있다. 클래스에 넣는 것만으로 오류 원인이 쉽게 발견되거나 객체를 교체하기 쉬워지는 것도 아니므로, 그런 장점은 별도의 설계가 뒷받침해야 한다.

## 4. 리스트와 반복문으로 고객 100만 명을 처리하는 코드가 느리다면?

> 동료가 만든 코드가 파이썬 리스트와 반복문으로 100만 명의 고객 데이터를 처리하는데, 실행하는 데 몇 분씩 걸려요. 이 코드를 어떻게 바꾸면 좋을지 진단하고, 구체적인 개선 방법을 제안해 주세요.

문제에서 굳이 리스트와 반복문을 언급한 것은, 배운 NumPy 배열을 활용해 보라는 의도라고 생각한다. 그렇더라도 **리스트를 사용했다는 사실만으로 느린 원인을 확정할 수는 없다. 먼저 어디에 시간이 걸리는지 측정할 것**이다.

예를 들어 전체 180초 중 데이터 읽기에 5초, 고객별 포인트 계산에 170초, 결과 저장에 5초가 걸렸다고 가정해 보자. 이 수치는 대화에서 설명을 위해 든 가상의 예시다. 이 경우에는 대부분의 시간을 쓰는 포인트 계산부터 살펴보는 것이 맞다.

고객별 구매 금액에 같은 비율을 곱하는 계산이라면, 숫자 데이터를 NumPy 배열로 만들고 배열 전체에 연산을 적용하겠다.

```python
# 기존 방식
amounts = [10000, 20000, 30000]
points = []
for amount in amounts:
    points.append(amount * 0.01)
```

```python
# NumPy 배열 전체에 연산을 적용하는 방식
import numpy as np

amounts_array = np.array(amounts, dtype=np.float64)
points = amounts_array * 0.01  # [100., 200., 300.], shape: (3,)
```

*고정 비율의 수치 연산을 설명하는 예시다. 실제 포인트 처리에서는 별도로 정한 반올림·절사 규칙도 지켜야 한다.*

### 배열로 바꾸면 왜 빨라질 수 있을까?

처음에는 리스트가 서로 다른 자료형을 담을 수 있으니, 다음 요소의 위치를 찾을 때마다 크기를 다시 계산해서 느린 것이라고 생각했다. 하지만 이 설명은 정확하지 않았다. 일반적인 CPython 리스트에는 **객체의 위치를 가리키는 참조가 일정한 크기로 나란히 저장**된다.

```text
리스트의 참조: [0x100, 0x500, 0x900]
                  ↓      ↓      ↓
가리키는 객체:    10     20     30
```

이는 임의의 주소로 그린 구조도다. 실제 파이썬 코드에 `[0x100, 0x500, 0x900]`을 쓰면 주소를 따라가는 것이 아니라 정수 세 개를 담은 리스트가 된다. `for num in numbers`의 `num`으로 다루는 것도 주소 숫자가 아니라 리스트가 참조하는 객체다.

리스트에서는 참조들이 나란히 있고, 각 객체까지 같은 순서로 나란히 놓인다는 보장은 없다. 반면 다음처럼 만든 NumPy 숫자 배열은 숫자 값 자체를 연속된 공간에 저장한다.

```python
numbers = np.array([10, 20, 30], dtype=np.int64)
```

```text
예시 주소    숫자 값
0x100        10
0x108        20
0x110        30
```

`int64`는 한 값이 8바이트이므로 다음 값의 시작 위치도 8바이트씩 이동한다. 각 값마다 별도의 파이썬 정수 객체를 찾아갈 필요가 없고, 가까운 데이터를 활용하는 CPU 캐시에도 유리하다. 다만 NumPy 배열도 일부 슬라이스나 전치로 만든 뷰는 연속적이지 않을 수 있다. `object` 자료형 배열도 일반 숫자 배열과 구분해야 한다.

### 벡터화는 반복을 없애는 것일까?

저장 구조만 바꾸는 것으로 설명이 끝나지는 않는다. NumPy 배열을 만들어 놓고도 파이썬 반복문으로 하나씩 계산하면, 파이썬이 요소마다 연산을 진행하는 부담은 남는다.

```python
result = numbers * 2
```

이 코드는 “숫자들의 묶음 전체에 2를 곱해 달라”고 표현한다. 수학에서 여러 성분을 순서대로 묶은 벡터에 연산을 적용하는 모습과 연결해서 벡터화라는 이름을 이해했다.

```text
2 × [10, 20, 30] = [20, 40, 60]
```

NumPy에서는 이렇게 요소별 반복을 배열 연산으로 표현하는 방식을 벡터화라고 부른다. 다차원 배열에도 같은 표현을 사용한다. 내부에서는 여전히 각 값을 계산하지만, 파이썬 반복문 대신 미리 컴파일된 연산 코드가 처리한다. **계산할 숫자의 개수가 사라지는 것이 아니라, 숫자 하나를 처리할 때 따라붙는 부담이 줄어드는 것**이다. 벡터화가 반드시 여러 스레드에서 동시에 계산한다는 뜻도 아니다.

### 다른 원인이면 다른 방법을 골라야 한다

고객 한 명을 처리할 때마다 전체 고객을 다시 검색하고 있다면, 배열로 바꾸기 전에 딕셔너리 등을 이용해 불필요한 반복 검색을 줄이는 방법을 검토하겠다. 외부 서버의 응답을 기다리느라 느리다면, NumPy로 숫자를 저장하는 방식을 바꿔도 그 대기 시간은 해결되지 않는다.

병렬 처리도 생각해 봤다. 하지만 일반적인 GIL 활성 CPython에서는 한 프로세스 안의 여러 스레드가 파이썬 코드를 동시에 실행하지 못한다. 따라서 파이썬 계산 반복문을 네 스레드로 나눈다고 네 코어에서 동시에 계산할 수 있는 것은 아니다. 프로세스를 나누는 방법도 있지만, 데이터를 나누고 전달하는 비용이 생긴다. 대기 시간이 많은 작업이나 GIL을 해제하는 NumPy 내부 연산은 조건이 또 다르다.

따라서 내 답변은 **먼저 병목을 측정하고, 반복적인 수치 계산이 원인이라면 NumPy 배열과 벡터화를 적용하겠다**는 것이다. 불필요한 반복 자체가 원인이라면 알고리즘을 먼저 바꾸고, 병렬 처리는 작업의 성격과 추가 비용을 보고 검토하겠다.

*게시를 위해 보완한 확인 기준: 변경 후에는 배열 변환 시간을 포함한 전체 실행 시간과 메모리 사용량을 비교하고, 결과 값·순서·누락 여부 및 필요한 수치 정밀도가 기존 요구를 만족하는지도 확인해야 한다. 이 비교를 실제 수행했다는 기록은 아니다.*
