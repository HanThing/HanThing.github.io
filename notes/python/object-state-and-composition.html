self.book_list라는 글자만으로는 어느 목록인지 알 수 없다. 지금 self가 누구이고, 그 속성이 어떤 객체를 가리키는지 따라가야 한다. 같은 목록 객체를 두 이름이 함께 가리킬 수도 있고, 서로 다른 목록이 같은 책 객체를 담을 수도 있다.

기본 호출 관계는 self-and-objects, 호출 종류와 타입 규칙은 methods-types-and-inheritance에 정리했다. 여기서는 9월 21일 복사·분류기 질문과 9월 22일 도서 대여 질문에서 반복된 상태 구분을 다룬다.

변수에는 객체를 가리키는 이름이 붙는다

a = [1, 2]에서 a는 리스트 객체를 가리키는 이름이다. b = a는 리스트를 복사하는 문장이 아니다. a와 b가 같은 객체를 가리킨다. 이후 a를 다른 리스트에 연결하는 것과 기존 리스트를 변경하는 것도 다르다.

이 보충 예제에서 append는 기존 객체를 변경했다. 두 번째 대입은 이름 a가 가리키는 객체를 바꿨다. b의 연결은 바꾸지 않았다. 이 관계를 이해하기 위해 모든 이름을 “스택”, 모든 객체를 “힙”이라고 단정할 필요는 없다. 구체적인 메모리 배치는 Python 구현에 관한 별도 문제다.

del a 역시 이름 연결을 지우는 동작이다. 다른 참조가 남아 있거나 순환 참조가 있는지, 어떤 Python 구현인지에 따라 객체 정리 시점이 달라질 수 있다. 소멸자가 즉시 실행된다고 일반화하지 않는다.

얕은 복사는 바깥 컨테이너를 새로 만든다

아래는 중첩 리스트를 비교하는 보충 예제다.

이름바깥 리스트내부 리스트관찰한 결과
alias원본과 같음원본과 같음내부 변경과 바깥 추가 모두 보임
shallow새 객체원본과 공유내부 변경만 보임
deep새 객체이 예제에서는 새 객체두 변경 모두 보이지 않음

“깊은 복사는 모든 값을 언제나 새로 만든다”도 정확하지 않다. 불변 객체는 재사용될 수 있고 사용자 정의 복사 동작도 있다. 여기서 확인한 것은 중첩 리스트의 공유 관계다. 값의 같음을 비교하는 ==와 같은 객체인지를 확인하는 is도 구별한다.

클래스 속성 조회와 인스턴스 속성 대입

다음은 특별한 속성 제어 기능을 정의하지 않은 일반 클래스의 보충 예제다.

처음 a.count를 읽을 때는 인스턴스에 그 속성이 없어 클래스의 0을 찾는다. 그다음 self.count += 1은 이 예제에서 a에 인스턴스 속성 count = 1을 만든다. 클래스의 count를 올린 결과가 아니다. Counter.count += 1로 클래스 쪽에 대입하는 동작과 구별해야 한다.

함수 안의 맨몸 count += 1도 별개다. 클래스 속성을 자동으로 뜻하지 않는다. 지역 변수로 판단된 count를 값이 연결되기 전에 읽으면 UnboundLocalError가 발생한다.

공유되는 가변 객체는 결과가 다르다.

append는 이 예제에서 클래스 속성이 가리키는 리스트 자체를 바꾼다. 객체마다 별도 목록이 필요하면 __init__ 안에서 self.members = []를 만들어야 한다. 클래스 속성과 인스턴스 속성의 차이를 숫자 예시 하나만으로 판단하면 이 공유를 놓치기 쉽다.

합성에서는 각 객체가 맡는 값과 동작을 따라간다

전처리·분류 실습은 하나의 거대한 객체 대신 역할을 나눈 객체들을 연결했다. 엔진이 파이프라인과 모델을 속성으로 보관하고 사용하는 관계를 합성으로 설명할 수 있다. 상속으로 엔진이 모델의 일종이 되는 관계와는 다르다.

flowchart LR
    A[TextSample] --> B[원문 문자열]
    B --> C[전처리 파이프라인]
    C --> D[처리된 문자열]
    D --> E[키워드 모델]
    E --> F[Prediction]
역할보관하거나 받는 값다음 단계에 주는 값
TextSample샘플 번호, 텍스트, 정답 라벨엔진이 속성에서 꺼내는 원문 문자열
전처리 파이프라인처리기 목록과 입력 문자열처리기를 차례로 적용한 문자열
키워드 모델분류 기준과 처리된 문자열python 같은 분류 문자열
Prediction샘플 번호, 원문, 처리된 문자열, 예측 라벨출력용 문자열 또는 속성값
엔진파이프라인과 모델두 객체를 순서대로 호출한 결과

이 표는 당시 실습의 역할을 요약한 것이다. 파이프라인 끝에서 return text가 빠지면 다음 단계에 None이 넘어간다. 엔진의 호출 문법이 맞더라도 단계 사이의 반환값 계약이 끊어진다.

반대로 Prediction.__str__에서 번호와 예측 라벨만 출력한다고 입력 속성이 없어진 것은 아니다. 객체가 보관하는 상태와 화면에 표현하는 문자열은 다른 범위다. 속성을 초기화하는 코드를 __str__ 안에 두면 객체 생성 시점에 필요한 상태가 준비되지 않을 수도 있다.

도서 목록 세 개는 같은 역할이 아니다

도서 대여 실습에서는 같은 이름 book_list가 서로 다른 클래스에 있었다. 목록의 소유자와 항목 타입을 먼저 고정하면 오류를 좁힐 수 있다.

상태소유자역할
전체 보유 도서도서관 객체대여 중인 책을 포함한 도서 목록
회원의 대여 목록회원 객체그 회원이 현재 빌린 책
대여 기록도서관 또는 대여 관리 객체어느 회원이 어느 책을 빌렸는지 연결

당시 최소 수정안에서는 회원 목록에 책 제목 문자열을 넣었다. 그러면 반납에서도 같은 제목 문자열을 찾아 지워야 한다. 다른 답변에서 제시한 Book 객체를 담는 방식을 중간에 섞으면 비교와 삭제가 어긋난다. 어느 방식이든 일관성이 필요하다.

아래는 두 컨테이너가 같은 책 객체를 담는 관계를 보여 주는 별도 보충 예제다. 당시 제목 문자열 구현을 그대로 옮긴 코드가 아니며, 완성된 도서 관리 프로그램도 아니다.

대여 목록에서 제거해도 전체 보유 도서 목록이 자동으로 사라지지 않는다. 서로 다른 리스트이기 때문이다. 별도의 대여 기록까지 저장한다면 그 기록도 함께 갱신해야 한다. 여러 곳에 같은 상태를 저장하면 한쪽만 갱신하는 실수가 생길 수 있다.

전체 보유 도서를 순회하면서 같은 목록에 찾은 책을 다시 append하는 것도 대여 처리가 아니다. 책이 중복된다. break가 없으면 순회 중 계속 길이가 늘어 끝나지 않을 수도 있다. 실제 질문의 마지막 코드에는 break가 있었으므로 그 상태를 곧바로 무한 반복이라고 부르면 안 된다.

퀴즈: 같은 객체인가, 같은 목록인가?

아래는 새로 만든 복습 문제다.

  1. first.items와 second.items는 각각 어떤 값인가?
  2. second.items = first.items로 바꾸었다면 마지막 결과는 어떻게 달라지는가?
  3. 원래 코드에서 item을 수정해도 두 번째 상자에 영향이 없게 하려면 무엇이 달라져야 하는가?
정답과 이유
  1. first.items는 [], second.items는 [{"count": 2}]다. 바깥 리스트는 별개지만 내부 딕셔너리는 공유했다.
  2. 두 속성이 같은 리스트를 가리키므로 clear() 뒤에 둘 다 []다.
  3. 내부 딕셔너리도 별도로 복사해야 한다. 이 구조에서는 deepcopy(first.items)를 사용하면 된다. 단순히 Box 객체 두 개를 만드는 것만으로 내부의 모든 객체가 자동 복사되지는 않는다.
