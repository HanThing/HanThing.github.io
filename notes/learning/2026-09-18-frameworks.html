라이브러리와 프레임워크의 차이가 왜 필요할까?

2026년 9월 18일6 min read

모듈과 패키지의 구조를 공부한 뒤 라이브러리·프레임워크로 질문이 이어졌다. 당시 웹 요청 흐름은 설명을 위해 든 가상 사례였으며, 사용자가 웹 프로젝트를 만들었다는 기록이 아니다.

질문 제목은 실제 발언의 뜻을 유지해 다듬었다. 의도는 사용자가 직접 밝힌 경우를 제외하면 대화 맥락을 바탕으로 정리한 해석이다.

질문: 외부 패키지를 라이브러리라고 부르는 걸까?

상황: 외부에 있는 패키지라서 라이브러리인지, 패키지가 여러 개 모여야 라이브러리인지 물었다.

의도: 모듈·패키지·라이브러리를 크기순의 고정 계층으로 이해해도 되는지 확인하려 했다.

핵심 답변: 패키지는 모듈을 묶는 구조를, 라이브러리는 가져다 쓰는 기능 모음을 가리킨다. 같은 대상을 두 관점으로 부를 수 있다. 외부 설치 여부나 패키지 개수만으로 라이브러리인지 결정하지 않는다.

당시 설명은 앞서 제시했던 “모듈 → 패키지 → 라이브러리”가 엄격한 계층처럼 보인 점을 정정했다. calculator는 구조상 패키지이면서 계산 기능을 제공하는 작은 라이브러리일 수 있다.

질문: 어차피 내가 실행하는데 제어의 역전은 말장난 아닐까?

상황: IoC 설명을 요청한 뒤, 내가 함수를 호출하든 프레임워크를 실행하든 결국 내 코드가 실행되는데 왜 구분하는지 물었다.

의도: “누가 호출한다”는 표현의 차이가 실제 구현 부담에 어떤 차이를 만드는지 알고 싶었다.

핵심 답변: 프레임워크를 시작하는 호출과 시작 이후의 실행 흐름을 관리하는 일은 다르다. 예를 들어 웹 프레임워크는 요청을 기다리고 적절한 사용자 함수를 호출한 뒤 응답을 보내는 흐름을 맡는다. 사용자는 그 흐름의 참여 지점에 자기 기능을 연결한다.

공통 흐름을 직접 구현하는 부담은 줄지만, 함수가 언제 호출되는지와 등록 규칙은 알아야 한다. 단순한 프로그램까지 반드시 프레임워크가 필요하다는 뜻은 아니다.

질문: 프로그램마다 흐름이 다른데 무엇이 공통이라는 걸까?

상황: 사용자는 프로그램 종류에 따라 흐름이 달라지는 예외를 지적했다. 이어 반복되는 처리가 이미 구현돼 있어 덜 신경 써도 된다는 이해가 맞는지, 제공 기능을 잘 파악하는 것 외에 어떤 이점이 있는지 물었다.

의도: 프레임워크가 유용한 범위와 자신이 여전히 맡아야 할 일을 확인하려 했다.

핵심 답변: 공통이란 모든 프로그램에 동일하다는 뜻이 아니라 비슷한 종류의 프로그램에서 반복된다는 뜻이다. 제공되는 흐름이 목적과 맞을 때 재사용하고, 다른 부분은 정해진 확장 지점에 연결한다. 틀에 맞지 않으면 다른 도구나 직접 구현이 더 나을 수 있다.

사용자는 “자주 반복되는 행위가 이미 구현돼 있어 신경을 덜 써도 된다”고 자기 말로 정리했다. 설명에서는 기능 목록뿐 아니라 연결 방법을 아는 것, 일관된 구조·공통 처리·개발 도구가 주는 이점도 보탰다. 이는 개념을 말로 다시 정리한 기록이며 특정 프레임워크 사용 능력을 검증한 것은 아니다.

관련 개념: 모듈과 패키지. 함께 읽기: import의 실행과 이름 연결.
